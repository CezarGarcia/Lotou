Pedido com cupom: tudo ou nada

Criar o pedido, gastar um uso do cupom, começar a saga e deixar a mensagem para o Kafka acontecem numa transação só. Se uma parte falha, nenhuma fica gravada.

order-service · banco orders
BEGIN
1
INSERT INTO orders … status 'PENDING'
o pedido nasce pendente, esperando o pagamento
2
UPDATE coupons SET uses = uses + 1
WHERE id = :cupom AND uses < max_uses
  AND status = 'ACTIVE' AND valid_until > now
a condição fica no próprio UPDATE: dois pedidos disputando o último uso não passam os dois
3
INSERT INTO coupon_redemptions
qual pedido usou o cupom e com quanto de desconto
4
INSERT INTO saga_state
a saga de compra começa, com prazo
5
INSERT INTO outbox: OrderCreated, AuthorizePayment
o relay publica no Kafka depois do COMMIT
COMMIT
havia uso sobrando
Segue até o COMMIT
  • pedido, uso do cupom, saga e mensagens gravados juntos
  • o pagamento começa pelo Kafka
nenhum uso sobrando
ROLLBACK
o cupom já atingiu o limite (ou foi pausado ou venceu)
  • o pedido é recusado: cupom esgotado
  • nenhuma das cinco escritas fica no banco
Rede de segurança: a tabela coupons tem CHECK (uses <= max_uses). Mesmo que o código errasse, o banco recusaria o uso a mais (ADR 33).
Cancelamento, a mesma ideia: pedido em reembolso, ingressos cancelados, passo da saga e mensagens no outbox, numa transação só.
